# 点媒体条弹出云听界面 —— 焦点归属排查

> **现象**（2026-11-02 实车）：本应用在播「四川交通旅游广播」，桌面左下角媒体条显示也正确，
> 但**点一下媒体条，弹出来的是云听 App 的播放界面**（里面显示的是「新闻有观点 / 中国之声」，
> 不是本应用正在播的台）。

---

## 1. 这张图能读出什么

| 位置 | 显示内容 | 说明 |
|---|---|---|
| 媒体条文字 | 「四川交通旅游广播 · 四川」 | **是本应用推的**（云听此刻在播中国之声，推不出这个台名） |
| 媒体条图标 | 台标 | 同上，来自本应用的 `getArtwork()` |
| 弹出面板 | 云听 logo + CMG 台标 + 「此歌曲暂无歌词」 | **是云听 App 自己的界面**，且内容是它自己恢复的台 |

两边内容不一致 —— 这就排除掉「云听抢了媒体条」，结论只有一个：

> **媒体条上的数据是我们的，点开时被路由给了云听。**

也就是说，「显示什么」和「点开谁」是两条独立链路，前者通了、后者没通。

---

## 2. 两条链路分别是什么

```
【显示】EasMediaCenter.updateMusicPlaybackState(token, info)
        → 车机媒体条画出 title / artwork / 状态      ← 这条一直正常

【点击】车机按「当前媒体源属主」决定启动哪个 App
        → 属主 = 持有播放焦点的那个客户端
        → api.queryCurrentFocusClient(token) 就能查到它是谁
```

所以我们注册成功、状态推得动，**并不代表点击就一定回到我们**：只要焦点在云听手上，
点击就打开云听。

### 酷我为什么是正常的

酷我 `onAPIReady` 之后只要在播就一直 `requestPlay` + `updateCurrentSourceType`，
它**始终是焦点的持有者**，所以点击自然回到酷我。它没有任何特殊的点击逻辑。

---

## 3. 我们的漏洞：焦点用「本地缓存」判断

v1.9.8 及以前的 `EasMediaCenter.push()`：

```java
if (playing && !hasFocus) {          // hasFocus 是「我抢到过」的记忆
    hasFocus = api.requestPlay(t);
    ...
}
```

`hasFocus` 一旦变成 `true` 就再也不复查。而云听这类常驻的在线音乐应用会在后台
自己再 `requestPlay` 一次，**焦点被它拿走，我们毫无察觉**：

- 缓存仍是 `true` → 那个 `if` 永远不成立；
- 既不会发现焦点丢了，也不会抢回来；
- 媒体条照旧显示我们的台（状态推送不受焦点影响），于是就成了截图里那个拧巴的状态。

---

## 4. v1.9.9 改了什么

| 改动 | 位置 | 说明 |
|---|---|---|
| **每次推状态前向车机复查真实焦点** | `EasMediaCenter.push()` → `queryFocus()` | 调 `api.hasFocus(token)`，不再只信本地缓存 |
| **焦点丢了立刻重抢** | 同上 | `requestPlay` 成功后再补 `updateCurrentSourceType`，把当前源类型落回我们声明的值 |
| **把焦点属主写进日志** | `logFocusOwner()` | 调 `api.queryCurrentFocusClient(token)`，直接打印「现在焦点在谁那儿」——这是「点开谁」的判断依据 |
| **注册后倒出车机媒体源表** | `dumpAppSources()` | 调 `api.getCustomAppSourceInfo()`，逐项打印包名 / `sourceTypeList` / `priorityLevel` / 是否运行中，用来判断 6（在线音乐）是不是被云听占着、谁优先级更高 |

`hasFocus` 查询失败时（老 SDK 没这方法 / binder 断了）退回本地认知，**不改变既有行为** ——
这条链路坏了不能拖累播放。

---

## 5. 上车怎么看

播放中打开诊断面板（运行日志），找这几行：

| 期望 | 日志 |
|---|---|
| 焦点被别人抢走了 | `[媒体源] 焦点已不在本应用，当前焦点属主 = <包名>` |
| 重抢成功 | `[媒体源] 重新 requestPlay 成功，当前源类型 → 6` |
| 重抢失败 | `[媒体源] 重新 requestPlay 被拒（对方仍持有焦点）` |
| 媒体源表长什么样 | `[媒体源] 媒体源表（N 项）：` 后面每行 `· <包名> 类型=[..] 优先级=..` |

三种结果对应三条下一步：

1. **属主是云听 → 重抢后变成我们**：问题解决，点媒体条应打开本应用。
2. **重抢被拒**：说明 6 这个 sourceType 的仲裁不只看 `requestPlay`。看媒体源表里
   云听的 `priorityLevel`，若明显高于我们，下一步要换一个没被占用的 sourceType
   （候选 8 `SOURCE_TYPE_STATION` / 9 `SOURCE_TYPE_NET_NEWS` / 12 `SOURCE_TYPE_ONLINE_RADIO`）。
3. **属主一直是本应用，点开还是云听**：说明点击不走焦点，而是走车机侧的
   `appSource` 配置（sourceType → App 的静态映射）。这条要看媒体源表里 6 归谁，
   必要时改 `/system` 的 appSource 配置（需要 root），或者退一步接受「点开是云听」。

---

## 6. 一句话总结

**显示靠 `updateMusicPlaybackState`，点击靠焦点属主。** 我们一直只保证了前者。
v1.9.9 补上后者：每次推状态前复查焦点、丢了就重抢，并把属主和媒体源表打进日志。
