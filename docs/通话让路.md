# 通话期间的方向盘按键让路（v1.9.6 → **v1.9.7 已更正**）

> ## ⚠️ v1.9.7 更正：本文第 1 节的归因是错的
>
> 逆向「星愿车控完全正常酷我音乐 6.0.0.9」后确认（详见 `docs/酷我车机版逆向分析.md`）：
>
> - 酷我**没有任何通话逻辑**：`PhoneStateListener` 0 处、`AudioManager.getMode()` 0 处、
>   `abandonPlayFocus` **0 处**、业务层 `setActive` 0 处；
> - 但它报的媒体源类型是 **6（在线音乐）**；我们报的是 **11（数字广播/DAB）**；
> - 车机对「调谐器一族」的上一曲/下一曲是**调台**，而且发生在 MCU 侧、不进 Android 分发。
>
> 也就是说：**按键不是被我们「持有焦点」吃掉的，而是被媒体源类型判成了调台。**
> v1.9.6 那套「通话时 abandonPlayFocus + setActive(false)」不仅没用，还会让媒体中心
> 把当前音源切回原车收音机，**把毛病做得更明显**。v1.9.7 已全部撤掉。
>
> 下面保留 v1.9.6 的原始分析，仅供追溯；**当前实现的判定请以 v1.9.7 与
> `docs/酷我车机版逆向分析.md` 为准**。

> **现象**：来电时按方向盘「下一曲」接听、「上一曲」挂断 —— 装本应用前可用，装上后失效，
> 两个键仍然在切电台。
>
> **v1.9.6 的结论（已被推翻）**：不是「电话那边坏了」，是我们成了**车机媒体中心的当前媒体源**，
> 车机按「谁持有播放焦点」派按键，所以这两个键从来没到过通话界面。

## 一、机制：按键到底是怎么被我们吃掉的

星愿车机的方向盘按键有**三条**路能落到我们手上，通话场景下三条都是错的：

| # | 路径 | 触发条件 | 原来的行为 | 通话时应该 |
|---|---|---|---|---|
| 1 | **EAS 媒体中心回调**<br>`EasMusicClient.onNext / onPrevious` | `registerMusic` 成功且我们持有播放焦点（**暂停也不还**，v1.9.1 的决定） | 一律 `return true` 并切台 | 不接，`return false` 交回媒体中心 |
| 2 | **`MediaButtonReceiver`**（清单里 `priority=2147483647` 的有序广播） | 系统发 `ACTION_MEDIA_BUTTON` | 处理完 `abortBroadcast()` | 原样放行，**连 abort 都不能调** |
| 3 | **`MainActivity.onKeyDown`** 私有码 346/347/348 | App 是焦点窗口 | 执行动作或只吞事件（都 `return true`） | 不拦，`return super` 交回系统 |

**真正致命的是第 1 条。** 第 2、3 条只是在「App 恰好在前台 / 恰好收到广播」时补刀；
而第 1 条是**常态**：QQ 音乐能在导航界面被方向盘控制，靠的就是这个机制 ——
媒体中心把按键翻成 `onNext` 回调，与前台窗口无关。同理，通话界面要拿到键，
前提就是**它不是被我们抢走的那一份**。

### 为什么不能靠「暂停时顺手还焦点」

v1.9.1 踩过坑：暂停时 `abandonPlayFocus` 之后，用户再按「播放」键**没有任何反应** ——
媒体中心手上已经没有当前源，不知道该派给谁（日志证据见 `EasMediaCenter.push()` 的注释）。
所以「暂停也保持焦点」是有意为之，不能为了修电话就整体推翻。

**唯一正确的做法是加一个明确的例外状态：通话期间让路，通话结束再抢回来。**

## 二、怎么知道「现在在通话」——不申请电话权限

电台应用申请 `READ_PHONE_STATE` 很怪，车机上还可能弹不出授权框，
所以 `TelephonyManager.getCallState()` 这条常规路走不通。改用两个**不需要权限**的信号：

| 信号 | 怎么读 | 覆盖什么 | 局限 |
|---|---|---|---|
| **音频模式** | `AudioManager.getMode()` | 通话 `MODE_IN_CALL`、VoIP `MODE_IN_COMMUNICATION`、**响铃 `MODE_RINGTONE`** | 依赖车机固件在通话时切模式（AOSP 与蓝牙 HFP 都会切） |
| **音频焦点被强制拿走** | `AudioFocusRequest` 回调收到 `AUDIOFOCUS_LOSS_TRANSIENT` | 车里播放的响铃/通话会以 `GAIN_TRANSIENT` 抢焦点 | 导航播报也会抢，需要靠时长区分 |

**为什么 `MODE_RINGTONE` 必须算通话**：用户是在**响铃阶段**按「下一曲」接听的。
只覆盖 `MODE_IN_CALL`（已接通）等于白修 —— 电话早就该接了。

**为什么要靠时长区分导航播报**：导航用 `GAIN_TRANSIENT_MAY_DUCK`，
我们收到的是 `LOSS_TRANSIENT_CAN_DUCK`（可以继续小声播），本来就不走这条分支。
但部分车机导航用普通 `GAIN_TRANSIENT`，所以对真正的 `LOSS_TRANSIENT`
再等 **2.5 秒**：还回来 → 当一声播报，不动；不还 → 当通话，暂停。

## 三、让路分两级，别合并

| 级别 | 判据 | 动作 | 生效时间 |
|---|---|---|---|
| **让键** | `CallGuard.shouldYieldKeys()`＝通话模式 **或** 焦点刚被拿走 | 三条路径都不处理、不吞事件 | **立即**（按键是毫秒级的事） |
| **让媒体源** | `CallGuard.isCallNow()`＝通话模式 **或** 焦点被拿走 ≥2.5s | 暂停、`abandonPlayFocus`、`MediaSession.setActive(false)` | 秒级（躲开导航播报） |

两级必须分开，合并任一方向都会出问题：

- 合并成「让键级」→ 导航播报一响就把电台停掉（v1.8.x 的老毛病）；
- 合并成「让媒体源级」→ 响铃头 2.5 秒按键还在我们手上，电话照样接不起来。

## 四、改了什么

| 文件 | 改动 |
|---|---|
| `CallGuard.java`（新增） | 判据中心。纯函数 `isCallMode / isCallNow / shouldYieldKeys`（可单测）+ 1 秒轮询音频模式 + 焦点变化入口 + 2.5 秒超时升级 |
| `RadioPlayer` | 新增 `onCallStarted()` / `onCallEnded()`；`callSuspended` 让 `activateSession()` 在通话期间不起作用（否则 `updateSessionState()` 会立刻把会话激活回来）；`pausedByCall` 记录「是通话让我停的」，挂断后只在这种情况下自动恢复；`onFocusChange` 把焦点事件转给 `CallGuard` |
| `RadioService` | 实现 `CallGuard.Listener`：进入通话先 `yieldForCall()` 再 `onCallStarted()`（先还焦点、后暂停，顺序反了会互相干扰）；结束时 `onCallEnded()` 后 `reclaimAfterCall()` |
| `EasMediaCenter` | 新增 `yieldForCall()` / `reclaimAfterCall()`：通话时 `abandonPlayFocus`，结束后 `requestPlay` 抢回；`push()` 里加保险，通话期间绝不 `requestPlay` |
| `EasMusicClient` | `onPlay / onNext / onPrevious / onSourceSelected / onMediaSelected ×2 / selectListMediaPlay` 通话时 `return false`（`onPause` 不拦：暂停永远安全） |
| `MediaButtonReceiver` | 通话时**不 abortBroadcast**、不处理、连服务都不拉起来 |
| `MainActivity` | 私有键 346/347/348、标准媒体键、`onKeyUp` 三处都在通话时 `return super`（DOWN 放行了 UP 也必须放行，否则通话界面看到的是「按下没松开」） |
| `CallGuardTest`（新增） | 把上面两级判据的真值表钉死，防止以后有人「顺手合并」 |

### 为什么要连 `MediaSession` 一起置为不活跃

会话活跃时系统会把媒体键路由给 `onMediaButtonEvent`。只暂停、不置不活跃的话，
按键照样进我们这里 —— 只是变成「给一位已暂停的电台切台」，电话还是接不起来。

## 五、上车怎么验证

装 v1.9.6，进 App 诊断面板（或 `adb logcat -s`）看这几行，顺序应该完全对得上：

```
来电响铃：
[通话] 音频模式 → 响铃(1)
[通话] 进入通话/响铃，开始让路：音频模式=响铃(1) 焦点被拿走=false 持续超时=false
[媒体源] 通话中：已交还播放焦点（方向盘按键回到通话界面）
[通话] 通话开始 → 已暂停，挂断后自动恢复
[通话] MediaSession 置为不活跃（媒体键交给通话界面）

按方向盘「下一曲」→ 应接听（我们这边一条日志都不该有）

挂断：
[通话] 通话结束，恢复按键与媒体源：音频模式=正常(0) …
[通话] 通话结束 → 恢复播放
[媒体源] 通话结束：重新抢回播放焦点 → true
```

**判断是否修好，只看两件事**：

1. 响铃时按「下一曲」是否接听 —— 这是主目标；
2. 挂断后方向盘是否还归收音机（切台/暂停要正常）—— 这是不能引入的回归。

如果第一件没成，看日志里**有没有**「音频模式 → 响铃(1)」：

- **有** → 说明让路逻辑跑了但车机不认，需要换招（见下节）；
- **没有** → 车机通话时不切音频模式、也不发 `LOSS_TRANSIENT`，判据拿不到信号，
  需要补第三个信号（见下节）。

## 六、已知不确定点（必须说清）

1. **车机固件是否在通话/响铃时切音频模式**：AOSP 与蓝牙 HFP（`HeadsetClientService`）
   都会切，但这是吉利定制 ROM，没有实车日志前不能断言。
2. **媒体中心是否认 `abandonPlayFocus`**：理论上焦点一还，按键路由立刻转走；
   但固件可能只在「用户切换媒体源」时才重算路由。
3. **若 1 和 2 都不成立**，下一步（按优先级）：
   - 申请 `READ_PHONE_STATE` + `TelephonyCallback.CallStateListener`，直接读通话状态
     （要加权限、要处理授权失败，属于「确实没别的办法了」才做）；
   - 或在车内实测出「响铃时系统广播」再挂接收器。

**这些都不能靠推理确定，只能上车验证。** 所以本版把日志写得比较密：
`[通话]` 前缀的每一行都是为这次排查准备的。
