# 闪退排查指南

> ## ✅ 已定位并修复（v1.8.2）
>
> 用户提供的 ColorOS 17 日志里，**9 次崩溃堆栈完全一致**：
>
> ```
> FATAL EXCEPTION: main
> java.lang.RuntimeException: Unable to get provider com.rea.radio.ApkProvider
>   at android.app.ActivityThread.installProvider(ActivityThread.java:10112)
>   at android.app.ActivityThread.installContentProviders(ActivityThread.java:9562)
>   at android.app.ActivityThread.handleBindApplication(ActivityThread.java:9158)
>   Caused by: java.lang.IllegalAccessException:
>     java.lang.Class<com.rea.radio.ApkProvider> is not accessible
>     from java.lang.Class<android.app.AppComponentFactory>
>     at java.lang.Class.newInstance(Native Method)
>     at android.app.AppComponentFactory.instantiateProvider(AppComponentFactory.java:151)
> ```
>
> **根因**：`ApkProvider` 声明成了 `final class`（漏 `public`）。
> 系统用 `Class.newInstance()` 实例化 Provider，要求 **public 且非 final**。
>
> 崩溃发生在 `handleBindApplication` 阶段，**早于 `Application.onCreate`**，
> 所以表现为「一点就退」，跟系统版本无关——手机上崩、车机上也崩是同一件事。
>
> **修复**：改成 `public class ApkProvider extends FileProvider`，并在
> `ComponentInstantiableTest` 里加了「从 Manifest 捞出所有组件逐个校验可反射性」的用例。
>
> 下面保留原始排查步骤，供以后参考（下次遇到类似问题照着走即可）。

---

## 原始排查思路（保留）

> 当时的现状：v1.8.0 在 **OPPO ColorOS 17** 和 **车机（Android 9）** 上都一打开就闪退。
> 这两台机器的系统版本差了 7 个大版本，**同一个原因同时命中两者的概率很低** ——
> 事后证明，这条推断是对的：真正的原因是「我的代码违反了系统反射规则」，
> 这种错误在任何 Android 版本上都会崩，与版本无关。
>
> 教训一句话：**「多台不同版本机器都崩」时，优先怀疑自己的包，而不是机器。**

---

## 第 1 步：先确认是不是"只崩这一次"（30 秒）

重装之后**第一次**启动最容易崩，因为要读旧版本的偏好数据。

1. 设置 → 应用 → 星愿收音机 → **强行停止**
2. 再点一次图标

| 结果 | 说明 | 下一步 |
|---|---|---|
| 第二次能正常打开 | 第一次崩在「读取上次状态」 | 装 **v1.8.1**（已加兜底），不用再往下查 |
| 每次点都闪退 | 是启动路径上的必崩点 | 继续第 2 步 |

---

## 第 2 步：确认是"我的包坏了"还是"机器环境问题"（1 分钟）

在车机上装 **v1.7.0**（`发布包/星愿收音机-v1.7.0-20261023.apk`）。

| v1.7.0 的表现 | 结论 |
|---|---|
| **也闪退** | 不是 v1.8.0 引入的。先排除安装包损坏（见第 5 步校验 SHA256），再查系统限制 |
| **能正常打开** | 是 v1.8.0 引入的，必须拿到堆栈才能修 → 第 3 步 |

> 手机上同理，装 v1.7.0 对比一下。

---

## 第 3 步：抓崩溃堆栈（这是唯一能精确定位的办法）

崩溃日志里一定有 `FATAL EXCEPTION` 和 `Caused by: xxx`。**没有堆栈，任何"我猜是××"都是在浪费时间。**

### 手机（OPPO ColorOS 17）

OPPO 自己就能导日志，不用装任何东西：

1. 设置 → 关于手机 → 连续点「版本号」7 次，开启开发者选项
2. 设置 → 系统设置 → 开发者选项 → 打开「**USB 调试**」
3. 数据线连电脑（**必须是数据线**，只管充电的线不行）
4. 手机弹窗点「允许 USB 调试」
5. 电脑上跑：

```bash
./scripts/crash_log.sh
```

### 车机（星愿 / Android 9）

车机一般没有 USB 调试入口，或者被厂商藏起来了。三个办法，从易到难：

1. **用同一个包在手机上复现**（推荐先试）：如果手机也崩，直接在手机上抓，堆栈是一样的
2. **装个日志查看 App**：车机上装「Logcat Viewer」之类的应用，闪退后打开看 `AndroidRuntime` 那几行，拍照发我
3. **U 盘 + adb**：如果车机能开 USB 调试（连续点版本号 → 开发者模式），用双公头 USB 线连电脑，跑同一个脚本

### 抓不到也没关系，把这三样发我也行

- 闪退**前**屏幕上显示的最后一个画面（哪怕只有一瞬间，拍照或录屏）
- 是「点图标后黑一下就退回桌面」，还是「白屏/黑屏停几秒才退」
- 车机上**是不是开机就闪退**（没点图标，自己弹出来又退）

---

## 第 4 步：怀疑安装状态残留时，彻底清干净

`adb install -r` 覆盖安装会保留旧数据，有时旧的 `SharedPreferences` 或缓存就是元凶。

```bash
adb uninstall com.rea.radio
adb install 发布包/星愿收音机-v1.8.1-20261023.apk
```

手机上手动操作：设置 → 应用 → 星愿收音机 → **存储 → 清除数据**（不是只清缓存），再重开。

如果清完能打开，说明是**数据损坏**，v1.8.1 的兜底修复正是针对这个场景。

---

## 第 5 步：确认安装包本身没坏

```bash
sha256sum 发布包/星愿收音机-v1.8.1-20261023.apk
```

应该等于 `releases/SHA256SUMS.txt` 里 v1.8.1 那行。不一致就是传输过程中损坏了，重新拷一次。

## 我这边已经修掉的（v1.8.1）

代码审查找到两个**确实会导致"一启动就闪退"**的隐患，都已修：

### ① `PlayPrefs.load()` 没有兜底 —— 最可疑

它在 `onCreate` 第 4 行被调用，是整个界面能不能起来的第一道门，但**原来一个 try/catch 都没有**：

```java
s.index = p.getInt(K_INDEX, 0);
```

如果存储里 `last_index` 这个 key 被写成过 String（版本升级改类型、或者文件被别的东西写过），
`getInt` 会抛 `ClassCastException` → 直接闪退，**而且每次启动都崩，用户连界面都进不去**。

有意思的是：同项目的 `FavoriteStore` 和 `HiddenStore` 都老老实实写了
`catch (Throwable)`，只有这个最关键的没有。

修复：整段包 try/catch，读失败就按"全新安装"处理。**恢复不了上次的台是小事，打不开是大事。**

> 这条修复有测试守着，而且做了变异验证（把修复撤掉，测试立刻变红）。
> 单测：`wrong_value_type_degrades_instead_of_crashing`

### ② 两处 `static final Handler MAIN = new Handler(Looper.getMainLooper())`

`static final` 字段在**类加载时**就初始化，而"哪个线程先加载这个类"是不确定的：

- `AppLog` 会被 `BootReceiver`（开机广播）先碰到
- `LogoLoader` 会被台标下载线程先碰到

一旦此时主 Looper 还没准备好（`getMainLooper()` 返回 null），`new Handler(null)` 直接抛 NPE。
更糟的是：静态初始化失败后，**之后每次访问这个类都会变成 `NoClassDefFoundError`**，整个应用彻底废掉。

修复：改成第一次用到时再建，并且允许"没有主线程"这种极端情况。

> 顺带修了 `LogoLoader.ensureInit()` 的并发竞态：原来是无锁懒加载，
> 多个台标线程同时首次进入会各自 new 一个 LruCache，先放进去的被覆盖。

## 还没排除的（需要堆栈才能继续）

以下这些我**看过代码但确认不了**，不能靠猜就改：

| 怀疑点 | 为什么没法确认 |
|---|---|
| Media3 ExoPlayer 在这两台机器上初始化失败 | 需要看堆栈里有没有 `ExoPlayer`/`MediaCodec` 相关的 `Caused by` |
| 车机厂商 ROM 限制了 `FOREGROUND_SERVICE` | Android 9 上应该没问题，但 ECARX 定制 ROM 有前科；要看 `ActivityManager` 那几行 |
| OPPO ColorOS 17 的后台限制杀掉前台服务 | ColorOS 会强杀，但正常应该只影响播放、不该闪退 |
| `usesCleartextTraffic` + 某些 ROM 的网络策略 | 只影响联网，不影响启动 |

**一句话结论：给我一份 `FATAL EXCEPTION` 堆栈，我能在 10 分钟内定位。在那之前，先装 v1.8.1 试一次——如果 ① 就是真凶，它已经修好了。**
