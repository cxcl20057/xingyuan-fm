# 方向盘按键与通知栏媒体控件

> v1.9.0 修前台、v1.9.1 修后台（接入 EAS 媒体中心）、v1.9.2 修媒体列表与卡片状态、
> v1.9.3 修「前台一次按键跳两台」。
> 本文记录完整排查过程、根因、四版修法，以及实测证据。
> **现在「切到导航/桌面」时方向盘也能控台，桌面小控件与媒体源清单页也能正常显示在播内容，
> 一次按键只切一台。**

---

## 一、结论先行

**星愿车机的方向盘按键不是标准媒体键，而是车厂私有键码（346 / 347 / 348）。**

框架里没有定义这三个码——`KeyEvent.toString()` 对它们打印的是数字本身而不是
`KEYCODE_XXX` 符号名，就是证据。框架不认识的 KeyEvent **不会**像媒体键那样
被全局拦截转给 `MediaSession`，只会派给当前焦点窗口的 `onKeyDown`。

所以：

- 之前那套 `MediaSession` + `MediaButtonReceiver` 链路**设计是对的**，但**从来没被用过**；
- 所有「加白名单」的路子（媒体中心数据库、appSource 配置、EAS 媒体源注册）
  都不是按键路由的判据，试了也没用。

**分版解决**：

| 版本 | 解决 | 机制 |
|---|---|---|
| v1.9.0 | 前台能控 | `MainActivity.onKeyDown` 里接私有键码 346/347/348 |
| v1.9.1 | 后台也能控 | 注册成车机媒体中心媒体源，收 `onPlay/onPause/onNext/onPrevious` 回调（第七章） |
| v1.9.2 | 卡片/清单能显示 | 补 `getPlayingMediaListId()` 等三个漏掉的字段 + 主动推媒体列表（7.8 节） |
| v1.9.3 | 前台不再跳两台 | 媒体中心接管后，前台私有键分支让位（7.9 节） |

## 二、按键链路真相

```
方向盘 CAN 信号
   ↓
com.android.car（CarInputService）注入 KeyEvent
   ↓  logcat tag: CAR.INPUT
      "onKeyEvent event:KeyEvent{...keyCode=348...} isCustomEventHandler:false"
   ↓
Android 输入管线（InputDispatcher）
   ↓  dumpsys input → RecentQueue 可见 KeyEvent
   ↓
焦点 App 的 Activity.onKeyDown(keyCode = 346 / 347 / 348)
```

## 三、键码实测表

| keyCode | 功能 | 证据 |
|---|---|---|
| `348` | 播放 / 暂停 | 两轮测试均以此键开头，与 347 成对出现 |
| `346` | 上一台 | 第一轮「上一台→下一台」顺序中的前者 |
| `347` | 下一台 | 第二轮只按「播放暂停+下一台」，出现 348→347 |
| `309` | 音量 + | 对照键，系统层正常处理（不是媒体键） |

标准媒体键对照（`input keyevent` 可注入、本应用也支持）：
`85`=播放暂停、`87`=下一首、`88`=上一首、`126`=播放、`127`=暂停。

> **无法用 `input keyevent 348` 在模拟器/设备上注入验证**：input 工具会校验键码范围，
> 超范围按 UNKNOWN 丢弃。所以单元测试只能验证「键码 → 动作」的映射表，
> 真实按键必须装车实测。

## 五、本次改了什么

### ① 补上私有键码分支（核心）

新增 `CarKeyCodes.java`，把键码表、判定、动作映射收在一处。
`MainActivity.onKeyDown` 里这段排在标准媒体键**之前**：

```java
if (CarKeyCodes.isSteeringWheelKey(keyCode)) {
    CarKeyCodes.Action act = CarKeyCodes.actionFor(keyCode);
    AppLog.key("按键", "方向盘私有键 keyCode=" + keyCode + " → " + act
            + " repeat=" + event.getRepeatCount());
    if (event.getRepeatCount() == 0 && act != null && player != null) {
        switch (act) {
            case TOGGLE: player.toggle(); break;
            case PREV:   player.prev();   break;
            case NEXT:   player.next();   break;
        }
    }
    return true;    // 无论 repeat 与否都吞掉
}
```

两个细节：

- **`repeatCount == 0` 必须判**。长按会连续产生 repeat>0 事件，不判断的话
  按住两秒能切掉十几台。
- **吞掉时不分 repeat**。私有码外面没人认识，交给 `super` 只会变成系统提示音
  或焦点乱跳，行为未定义。

同时补了 `onKeyUp`：只重写 `onKeyDown` 是不够的。一次物理按键会先发 ACTION_DOWN
再发 ACTION_UP，DOWN 被消费了，UP 如果没人管会继续往上传给系统。

### ② 通知绑定 MediaSession（修「通知栏媒体控件点了没反应」）

原状态：通知用了 `Notification.MediaStyle`，**但从来没调过 `setMediaSession(token)`**。

后果是那个通知只是「长得像媒体控件」的普通通知——系统不知道按钮该派给谁，
车机媒体中心也不认为这是活跃媒体。

```java
Notification.MediaStyle style = new Notification.MediaStyle()
        .setShowActionsInCompactView(0, 1, 2);
if (player != null && player.sessionToken() != null) {
    style.setMediaSession(player.sessionToken());   // ← 以前缺这句
}
b.setStyle(style);
```

### ③ 停播后释放会话（修「按键派给空会话」）

原 `stop()` 只改 `PlaybackState`，metadata 一直挂着上一个台的台名和台标。
于是会话看上去还是「有个正在播放的台」，系统继续把它当活跃媒体，
方向盘按键会继续派进来但没有任何反应。

现在 `stop()` 里清 metadata + `setActive(false)`，把媒体键让给真正在播的应用。

配套加了 `activateSession()`：`setActive(false)` 之后系统不再往这里路由媒体键，
所以凡是**要恢复播放**的路径都得先激活。除了 `resume()` 显式调用，
`updateSessionState()` 里还有一道兜底（只要 `playWhenReady || opening || prepared`
就激活），免得将来新增播放路径时忘了。

### ④ 不再把 `onSeekTo` 当切台

旧实现把 `onSeekTo` 映射成 `next()`，理由是「车机进度条拖动总得有点反应」。
但这会造成误触：锁屏拖一下进度条、媒体卡片误滑，都变成换台。

现在 `onSeekTo` 只记日志。同时 `PlaybackState` 里位置填 0 且不声明
`ACTION_SEEK_TO`，系统就不会画可拖动的进度条——直播本来也没有进度可言。

## 七、v1.9.1：后台也能控（接入 EAS 媒体中心）

v1.9.0 修的是「前台」。`onKeyDown` **只在 App 是焦点窗口时触发**，
切到导航/桌面时按键送给当时的焦点窗口 → 方向盘失效。
这一章记录 v1.9.1 怎么把它彻底解决。

### 7.1 思路：让媒体中心替我们收按键

星愿车机的方向盘按键由 `com.android.car` 处理，它先去问车机自己的媒体中心
（`ecarx.xsf.mediacenter`）「当前媒体源是谁」：

```
方向盘 CAN → com.android.car（CarInputService）
   ├─ 当前有活跃媒体源（注册过 + 声明在播）→ 翻译成媒体操作，回调给该媒体源的客户端
   └─ 没有 → 按键落到焦点窗口（v1.9.0 走的就是这条）
```

所以只要注册成媒体源并持有播放焦点，**App 在后台也能收到
`onPlay / onPause / onNext / onPrevious`**。QQ 音乐、网易云走的就是这条路；
顺带的副作用正好是「桌面左下角常驻一个小播放控件」—— 那东西就是媒体中心的当前媒体源卡片。

### 7.2 SDK 从哪来

不在系统框架里（`/system/framework/AdapterAPI.jar` 只有车控 API，`mediacenter` 命中 0），
是每个音乐应用各自打包的 `com.ecarx.eas.*` / `ecarx.xsf.mediacenter.*` 媒体中心 SDK。

本公开仓库**不包含**该 SDK 的二进制（`app/libs/eas-sdk.jar`，约 955 个类、860 KB）。
如需接入车机媒体中心，请自行准备该 jar 放到 `app/libs/` 下后再构建。

该 SDK **不需要系统签名**：引用它的应用均安装在 `/data/app`，清单里也没有任何 EAS 权限声明。

### 7.3 三个必须知道的坑（都是实测撞出来的）

**① `registerMusic(IMusicClient)` 是空壳，必须用「类版」**

SDK 里两套 API（接口版 `IMusicClient` / 类版 `MusicClient`），但
`MediaCenterProxy.registerMusic(IMusicClient)` 反编译出来只有两句：

```
0: aconst_null
1: areturn          // 永远返回 null
```

实测日志（踩坑现场）：

```
[媒体源] EAS 框架就绪回调：true
[媒体源] registerMusic 返回 null（框架还没连上？）稍后重试
```

框架其实已经连上了，是这个重载压根没实现。真正转发到服务的是
`registerMusic(MusicClient, RegisterRequest)`。

**② `MusicPlaybackInfo` 的 34 个 getter 全是 `return null`，必须继承覆盖**

类版要求 `getMusicPlaybackInfo()` 返回 `MusicPlaybackInfo`，而这个类里每个 getter
都是硬编码返回 null/0（框架反序列化用的空壳 DTO），第三方填不进值。
解法是继承它、把有用的 getter 覆盖掉，靠**协变返回类型**满足类版签名
（见 `EasPlaybackInfo`）。

**③ 暂停时**不能**还播放焦点**

第一版逻辑是「在播就 `requestPlay`，暂停就 `abandonPlayFocus`」。上车实测：

```
[媒体源] 媒体中心 onPause
[媒体源] abandonPlayFocus（还回播放焦点）
[播放] 已暂停
（之后再按播放键：一条日志都没有）
```

焦点一还，媒体中心手上就没有当前源了，**播放键不知道派给谁** ——
方向盘的暂停成了单向操作。改成：焦点只在媒体中心明确把我们切走
（`EasMusicClient.onExit()`）时才还；暂停期间保留焦点。
用户切到 QQ 音乐时，对方会自己 `requestPlay` 抢走，不需要我们主动让。

### 7.4 代码落点

| 文件 | 职责 |
|---|---|
| `app/libs/eas-sdk.jar` | 从网易云提取的 EAS SDK（唯一入库的二进制依赖） |
| `EasMediaCenter.java` | 连接框架 → `registerMusic` → 抢焦点 → 推状态；所有 SDK 调用包 `try/catch (Throwable)` |
| `EasMusicClient.java` | 继承 `MusicClient`，把 `onPlay/onPause/onNext/onPrevious` 回主线程转给 `RadioPlayer` |
| `EasPlaybackInfo.java` | 继承 `MusicPlaybackInfo`，覆盖 getter 造状态快照 |
| `EasBridge.java` | 纯 Java 的空接口，让 `RadioPlayer` 编译期看不到任何 `com.ecarx` 类型（否则 JVM 单元测试加载就炸） |

接线两处，都只有一行：`RadioService.onCreate` 里 `EasMediaCenter.install()`，
`RadioPlayer.updateSessionState()` 末尾 `EasBridge.push(this)`（状态唯一出口，
所以不会出现「通知栏对了、媒体卡片还是上一台」）。

### 7.5 状态字段怎么填

| 字段 | 值 | 为什么 |
|---|---|---|
| `sourceType` | `SOURCE_TYPE_ONLINE_RADIO`（12） | 语义就是网络电台。用 `SOURCE_TYPE_FM`(3) 会被当成车机物理调谐器，切源时可能去抢硬件通道 |
| `radioStationName` / `title` | 台名 | 部分界面（仪表、语音）只读电台专用字段 |
| `duration` / 进度 | 0 | 直播没有总时长。填真实秒数会画出可拖动的进度条，一拖就 seek |
| `artwork` | `null` | 台标在本应用私有目录，媒体中心是另一个 uid 读不到；塞了读不到的 Uri 会显示空白块 |
| `paused` 时的焦点 | **保留** | 见 7.3 ③ |

结论：**App 在后台（桌面聚焦 Launcher）时，三个键全部生效。**

| 操作 | 证据 |

# 桌面截图看常驻控件

### 7.7 注册失败怎么自愈（写完自查才发现的一个漏洞）

初版实现是「失败重试 5 次，间隔递增（0.8s / 2s / 5s / 10s / 30s），试满就放弃」。
打包前自查时发现这在**真实使用路径上是个漏洞**：

```
开机 → BootReceiver 拉起 RadioService → EasMediaCenter.start()
                                        ↑ 此刻媒体中心可能还没起
     → 48 秒内连不上 → 放弃 → 本次开机永久没有后台方向盘
```

车机冷启动时 `ecarx.xsf.mediacenter` 比第三方应用晚起是**常态**，所以「永久放弃」不可接受 ——
用户不会知道「要手动重开一下 App」。

最终改成三级：

| 阶段 | 节奏 | 写日志 | 目的 |
|---|---|---|---|
| 快速 | 0.8s / 2s / 5s / 10s / 30s，共 5 次 | 写 | 服务短暂重启这类故障能快速接上，且失败原因可诊断 |
| 慢速 | 每 3 分钟一次，直到成功 | **不写** | 跨过媒体中心启动慢的时间窗；手机上永远连不上，写日志只会挤掉诊断面板的有用信息 |
| 补试 | 播放状态变化且距上次尝试 > 3 秒 | 不写 | 用户按键就是「我现在要用」，这时补试比等 3 分钟合理 |

两个实现细节，都是踩过才写下来的：

- **同一时刻只允许一个重试任务排队**（先 `removeCallbacks` 再 `postDelayed`）。
  否则 `onAPIReady` 回调和重试定时器会叠加，一次失败可能触发两条重试链。
- **重试任务里发现 `api == null` 要重新 `start()`**（先把 `initStarted` 复位）。
  `MediaCenterAPI.get()` 本身也可能抛（媒体中心进程没起），这时 `register()` 只会空转。

`uninstall()` 里置 `disposed` 并 `removeCallbacksAndMessages(null)`：
`RadioService` 是 `START_STICKY`、会被系统反复重建，不清理的话旧实例一直被 Handler 队列攥着。

> ⚠️ **这一处没有上车验证过**（改完时车机不在线），属于静态自查 + 编译通过。
> 失败模式是安全的：最坏情况退回「v1.9.0 的前台行为」，不会崩、不影响播放。

### 7.8 媒体列表与「清单页空白」（v1.9.2）

v1.9.1 上车后暴露出两个看着无关的现象，其实是同一个根因：

| 现象 | 位置 |
|---|---|
| 播放时显示播放按钮、暂停时还是播放按钮 | 桌面左下常驻小控件 |
| 「当前暂无播放内容」 | 点媒体源清单进去的弹窗 |

#### 媒体中心靠三件套定位「当前媒体」

| 字段 | v1.9.1 的值 | 媒体中心的理解 |
|---|---|---|
| `mediaId`（来自 `MediaItem.id`） | `490` 有值 | 有个东西在播 |
| `mediaQueueId`（来自 `getPlayingMediaListId()`） | **`null`** | 它不属于任何列表 |
| 列表内下标 | 有值 | 没有列表，下标无意义 |

于是：清单页的字面意思就是「某个列表的内容」，列表 id 空 → 没东西可列；
卡片按钮要知道「当前项在列表里的位置」才能画成「播放中点一下暂停」，定位不到就退化成未播外观。

> **为什么能确定 `mediaQueueId` 只能从这里来**：翻了 `ecarx.xsf.mediacenter.session.PlaybackInfo`
> 和 `MediaItem` 两个服务端 bean，**都没有状态/队列字段**
> （`PlaybackInfo` 只有 appId/appName/iconUri/initialProgress/launchIntent/mediaItem/pkgName/playerIntent/zoneId）。
> 而 `com.flyme.auto.mediacontrol`（左下小控件那个 APK，
> `com.flyme.auto.mediacontrol.datacenter.bean.mediacenter.MediaStateBean`）
> 里明确有 `mediaId` / `mediaQueueId` / `playSate(PlayState)` 三个字段。
> 也就是说 `mediaQueueId` 的唯一上游就是 `getPlayingMediaListId()`。

#### 漏在哪

`AbstractMusicPlaybackInfo` 一共 **35 个 abstract 方法**，v1.9.1 覆盖了 32 个，漏的 3 个是：

```java
getPlayingMediaListId()      // → null
getPlayingMediaListType()    // → 0
isSupportVrCtrlPlayStatus()  // → false
```

前两个正是列表归属。教训：**改这种空壳 DTO 时，用 `javap | grep abstract` 数一遍个数再对，别靠"用到哪个补哪个"。**

#### 同一片区域里另外三个错（都已改）

| 之前 | 问题 | 现在 |
|---|---|---|
| `getPlaylist()` 返回空表 | 注释写着「本应用没有列表概念」——**判断错了**，队列就是列表 | 返回真实队列快照 |
| 没覆盖 `getMultiMediaList(int[])` | 父类返回 `null`；而清单页**优先走这个**，不是 `getPlaylist` | 返回含一个列表的 `MediaListsInfo` |
| 从不调 `updateMediaList()` | 只等它来拉，而所有拉取入口都是空的 | 队列/下标变化时主动推 |

另外 `onMediaSelected` 有**两个重载**，清单页实际传的是 `onMediaSelected(int sourceType, String mediaId)`，
只覆盖 `onMediaSelected(MediaInfo)` 等于没接 —— 现在两个都覆盖，按 `contentId` 定位。

#### 一个省事的发现：SDK 自带带 setter 的 bean

`MediaInfo`（29 个 abstract）和 `MusicPlaybackInfo`（35 个 abstract）都是空壳 DTO，但 SDK 里同时有：

- `MediaInfoWrapper extends MediaInfo` —— 18 个 getter + 对应 setter
- `MediaListInfoBean extends MediaListInfo` —— 列表 bean，setter 齐全
- `MediaListsInfo` —— 本来就有 `setMediaListsInfo()`

所以构造列表项**不用**自己继承覆盖 18 个 getter，`new MediaInfoWrapper()` 直接填。
（`MusicPlaybackInfo` 没有对应的 wrapper 版，仍得靠 `EasPlaybackInfo` 继承覆盖。）

#### 推送顺序

`push()` 里是「先 `updateMediaList` 再 `updateMusicPlaybackState`」。
反过来的话会有一瞬「有状态但没列表」的窗口，详情页会闪一下「暂无播放内容」。

列表指纹 = `项数 | 首项 id | 当前下标`，只有变了才重推 —— 否则「暂停一下」也要把几十项全表过一遍 Binder。

### 7.9 两条路径会打架：一次按键跳两台（v1.9.3）

**现象**（2026-10-26 用户反馈）：App 在前台时按一下「下一台」，跳**两个**台。

**证据**（v1.9.2，`logcat` 原文，同一次按键）：

```
07:35:45.519  27621  27621  [按键] 方向盘私有键 keyCode=347 → NEXT repeat=0
07:35:45.519  27621  27621  [播放] 切台 → 经济之声
07:35:45.752  27621   3026  [媒体源] 媒体中心 onNext          ← Binder 线程
07:35:45.753  27621  27621  [播放] 切台 → 环球资讯广播
```

两条日志的 tid 不同（主线程 vs Binder 线程），间隔 **233ms**。

**根因**：媒体中心对方向盘按键是**广播式**派发 —— 既派给当前焦点窗口的
`onKeyDown`，**也**派给所有注册过的媒体源。v1.9.0 的前台分支和 v1.9.1 的 EAS
回调同时活着，所以前台时两份都被执行。

| 场景 | v1.9.0 前台分支 | v1.9.1 EAS 回调 | 结果 |
|---|---|---|---|
| App 在前台 | ✅ 执行 | ✅ 执行 | **跳 2 台** ❌ |
| App 在后台 | ✗ 收不到 | ✅ 执行 | 跳 1 台 ✅ |
| 注册失败/非星愿 | ✅ 执行 | ✗ 无 | 跳 1 台 ✅ |

**修法**：`EasBridge` 加一个 `active` 标记，`registerMusic` 成功拿到 token 时
`setActive(true)`，`uninstall()` 时 `setActive(false)`。前台分支变成：

```java
boolean byMediaCenter = EasBridge.isActive();
if (!byMediaCenter && event.getRepeatCount() == 0 && act != null && player != null) {
    switch (act) { case TOGGLE: ...; case PREV: ...; case NEXT: ...; }
}
return true;   // 无论谁接管都吞掉事件
```

**为什么不是直接删掉前台分支**：`active` 只在注册**成功**后为真。非星愿车机、
媒体中心进程还没起来、服务刚被系统重建 —— 这些情况下前台分支是唯一能用的路径。
用运行时的 `isActive()` 判断，两个场景都兼顾。

> 同一个 bug 也会让**播放/暂停键表现成「按了没反应」**：`TOGGLE` 被连执行两次
> 就是「暂停又立刻播放」，净效果等于什么都没发生。修完这个，暂停键才真正可用。
> 所以「跳两台」和「播放键不灵」如果是同一批出现的，先怀疑这里。

**实测**（2026-10-26，车上，v1.9.3）：

| 操作 | 日志 | 结果 |
|---|---|---|
| 注入 `347` ×1 | 只有 `媒体中心 onNext` | 环球资讯广播 → 音乐之声（第 3 → 第 4 项）✅ |
| 按 `348` ×1 | `[按键] …（媒体中心已接管，此处仅吞事件）` + `onPause` | 只暂停一次 ✅ |
| 再按 `348` | `onPlay` | 恢复播放，`state=3` ✅ |

**附带清理**：车上曾同时装着 `com.rea.radio` 和 `com.rea.radio.debug`，
两个包各自注册成媒体源、互相抢播放焦点。调试用的 `.debug` 包验完就该卸掉：

```bash
adb -s 192.168.9.141:5555 uninstall com.rea.radio.debug
```

### 7.10 风险与回滚

- **厂商升级可能改接口**：SDK 是逆向提取的，媒体中心升级后 `IMediaCenterClientToken`
  或 `RegisterRequest` 形态变了就可能注册失败。所以所有调用都吞异常，
  失败时**完整降级为 v1.9.0 的前台行为**（不会崩、不会卡）。
- **想彻底关掉 EAS**：删 `RadioService.onCreate` 里那一行 `EasMediaCenter.install()` 即可，
  `EasBridge.push` 会变成空操作，其余代码不用动。

## 八、装机后怎么验

### 8.1 前台路径（v1.9.0 起）

```bash
# 装好后打开 App，按方向盘三个键
adb logcat -s XingyuanRadio | grep 按键
```

v1.9.3 起，媒体中心接管后这里打印的是**带说明的让位日志**（事件仍然吞掉，但不执行动作）：

```
[按键] 方向盘私有键 keyCode=348 → TOGGLE repeat=0（媒体中心已接管，此处仅吞事件）
```

真正执行动作的是紧接着的 `[媒体源] 媒体中心 onPause / onNext / onPrevious`。

**媒体中心没接管时**（非星愿车机、注册还没成功），打印的是：

```
[按键] 方向盘私有键 keyCode=347 → NEXT repeat=0（前台处理）
```

这一行后面会跟一条 `[播放] 切台 → …`，说明走的是前台路径。

> 判据看括号：`（前台处理）` = 本分支自己执行；`（媒体中心已接管，此处仅吞事件）`
> = 交给 EAS 执行。两者**只能出现一种**，同时执行就是 v1.9.3 修掉的那个双触发 bug。

**完全看不到 `[按键]` 行**说明按键没到焦点窗口（但可能仍被媒体中心派发，
接着看 8.2）。用 `adb shell dumpsys input | grep -A5 RecentQueue` 确认按键进没进输入管线。

**看到了但没反应**说明 `player` 为 null（服务没起来），看 `[服务]` 相关日志。
